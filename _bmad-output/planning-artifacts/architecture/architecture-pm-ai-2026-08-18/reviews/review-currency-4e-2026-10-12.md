# Currency review — 2026-10-12 amendment, slice 4e (the daemon)

Lens: is every external fact the amendment and the code it describes rely on checked against reality (the installed packages, the live registry, this machine), not asserted from memory?

Scope: the spine diff (AD-5 "the daemon keeps the claim", the closed "There is no daemon" gap row, the narrowed plaintext-warning risk), `pm_ai/app/daemon.py`, `pm_ai/surfaces/api/app.py`, the operational-store busy handling in `pm_ai/storage/service.py`, `pyproject.toml`, `uv.lock`.

## Verdict

Almost every external behaviour holds. I checked each one against the installed uvicorn 0.52.3 / starlette 1.6.0 / fastapi 0.141.1 source, against runs on this machine (Python 3.14.7, SQLite 3.53.1, macOS, x86_64 under Rosetta), and against today's IANA registry. Three things need fixing: the IANA range quoted for 8747 is wrong, one SQLite busy case is refused without the wait the amendment and the error message both promise, and starlette is not pinned directly.

## Findings

1. **The IANA range is misquoted, so it was transcribed rather than read.** `_bmad-output/specs/spec-pm-ai/stories/4e-daemon-and-loopback-api.md:24` and `pm_ai/core/config.py:262` both say "8732-8749 Unassigned". The registry says 8734-8749. The conclusion, that 8747 is unassigned, still holds. **Fix:** quote "8734-8749 Unassigned (IANA registry last updated 2026-10-09)" in the code comment, and correct the story through the skill. Also note that unassigned means unregistered, not unused locally, and that the doctor/refusal path already covers a port that is taken.

2. **One busy refusal comes without the wait, and its message says otherwise.** Under WAL, a transaction that has read and then tries to write after another connection committed gets `database is locked` immediately: SQLite skips the busy handler for a stale snapshot. Measured: 0.0 s, against 5.4 s for an ordinary blocked write. pm-ai has no explicit `BEGIN` today, and legacy transaction control issues the implicit `BEGIN` only before DML, so no current path hits this. The amendment's sentence and `_OperationalConnection._busy`'s wording ("for the whole busy wait (5000 ms)") are still unconditional. **Fix:** in the spine, say "a write refused as busy, whether after the wait or at once because its snapshot went stale, is refused by name". In the message, drop "for the whole busy wait" or say "was refused as busy (busy wait configured: 5000 ms)". Alternatively, add a constraint: no read-then-write transaction without `BEGIN IMMEDIATE`, which `4r` will need anyway when it adds job-queue transactions.

3. **Starlette is resolved only through fastapi's floor.** fastapi 0.141.1 declares `starlette>=0.46.0`, and pyproject pins fastapi and uvicorn with `==` but not starlette. `uv lock --upgrade` (or any re-lock) can move starlette across a major version while the spine's pinning policy appears satisfied. The ASGI wrapper does not depend on starlette internals, but `FastAPI(lifespan=...)` and the docs-route switches go through it. **Fix:** pin `starlette==1.6.0` in the runtime extra next to the other two, or record in the spine that it floats on purpose under the lock.

4. **The `sockets=` path's startup error is not wrapped.** In uvicorn 0.52.3 `create_server(sock=...)` is not inside the `try/except OSError → sys.exit` that the host/port branch has. A failure there escapes `serve()` as a raw `OSError`, not as `DaemonRefused`, despite the docstring's "raises `DaemonRefused` for every reason it will not start". It is unlikely with a socket already listening, but the docstring's promise relies on uvicorn behaviour that holds on only one of its branches. **Fix:** add `except OSError` around `asyncio.run(...)` that wraps the error in `DaemonRefused` naming the port.

5. **The override reaches into uvicorn's private surface.** `capture_signals`, `handle_exit` semantics and `startup(sockets=)` are not documented API. They are verified identical from 0.52.3 to 0.54.0, but nothing would flag a change. **Fix:** a small test that asserts `uvicorn.Server.capture_signals` exists and still references `signal.raise_signal`, or simply the existing SIGINT/SIGTERM/SIGHUP exit-0 tests if they run against the real uvicorn. Record in the spine's Stack entry that bumping uvicorn means re-checking these. The re-raise-to-exit-code-3 rationale in `_server_class`'s docstring was not reproduced here: only the re-raise itself was confirmed.
